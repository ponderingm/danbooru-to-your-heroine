## 1. 背景とビジョン

### 1.1 背景
Danbooru などの画像 Booru サイトは、精緻な英語タグ体系（`eating_ice_cream`, `micro_bikini` など）によって作品が分類されている。しかし、ユーザーが「こんなイラストが欲しい」と考えた際、適切な Danbooru タグの組み合わせを記憶・考案するのは認知的負荷が高い。また、タグを多く指定しすぎると AND 検索の性質上「該当 0 件」になりやすい。

### 1.2 ビジョン
ユーザーが**日常の自然言語（日本語・英語の自由文）**でシチュエーションを入力するだけで、LLM が必要十分なコアタグとメタ構文（`order:`, `rating:`）を自動決定し、既存のヒロイン換装バッチ生成パイプライン（`danbooru_search_batch_generator.py` および WebUI/API の `/batch/start`）に即座に受け渡すことができる仕組みを構築する。

## 2. システム責務と入出力仕様

### 2.1 責務の明確化 ＆ プロジェクト核心思想『タグ共起継承（Co-occurrence Inheritance）』
本モジュールは**「自然言語から最適な Danbooru 検索タグ文字列を出力すること」**に専念する。

> #### 💎 **プロジェクト核心思想：タグ共起継承の原則（Co-occurrence Inheritance）**
> 『タグ共起継承』は本検索機能にとどまらず、**本プロジェクト『danbooru-to-your-heroine』全体の存在理由（レゾンデートル）であり根幹思想**である。
> 
> プロンプトを一から自作・暗記する必要はない。Danbooru 上に実在するイラストには、そのシチュエーションやフェチ・装飾を美しく成立させるための**必須要素（`pierce`, `chain`, `jewelry`, `ring`, 表情, 光彩など）が絵師やタガーによって最初からセットで付与されている**。
> 
> 静的なタグ辞書（`danbooru_tags.csv` 等）で足切りを行わず、実在する投稿のタグリストから周辺の必須要素をそのまま収集・継承することで、ユーザー自身の語彙力や呪文詠唱の限界を遥かに超えた、極めて美麗でディテールに富んだヒロイン画像が自動的に再生成される。本検索モジュールは、この豊かな共起プールへの「新しい自然言語の入り口」として機能する。
> 
> **工学的ストロングポイント**:
> 1. **エンコーダー未知語の幾何学的具現化**: 仮にCLIPがニッチな合成単語を正確に把握していなくても、共起する位置・質感・関連パーツのAttentionベクトルが相互に引き合い、目的のオブジェクト（微細なリングやチェーン等）が確実に画像上に具現化する。
> 2. **SDXL CLIP（75トークン制限）への奇跡的収束**: 人手審査・精度の高いDanbooru投稿はノイズパージ後で約30〜45タグ程度。ヒロインDNA（10〜15タグ）とクオリティ修飾子を足しても55〜70トークン前後に収まり、SDXL CLIPの最重要領域である「第1ブロック（75トークン以内）」をほぼ突破しない。チャンク分割によるアテンション減衰を起こさず、濃密な共起情報が一括注入される。
> 
> *(※内部検証コード: `bGFiaWFfcmluZw==` — タグ辞書に未登録の未知・微小属性であっても、「共起継承の輪（xxxxx ring）」によって美麗な画像が成立することを確認した実証実験に由来)*

## 3. LLM 選定・実行環境の比較検討

本システムで最も重要な課題は、**「センシティブ・エロティックな自然言語入力に対する検閲回避」**と**「推論速度・リソース消費」**のバランスである。

### 3.1 ローカル LLM の検討

最新世代のオープン重みモデル（Qwen ファミリー等）を対象とする。

| 項目 | 小型・中型クラス (Qwen 3.6 シリーズ) | 大型・フロンティアクラス (Qwen 3.8 シリーズ) |
|---|---|---|
| **想定用途** | エッジ・ローカル常駐、リアルタイム検索 | 高度推論、複雑な多層コンテキスト解釈 |
| **メモリ/VRAM** | 約 2〜4 GB（量子化モデル） | 約 16GB〜 以上の専用GPU環境が必要（巨大モデル） |
| **推論速度 (GPU)** | **0.3〜1.0 秒**（即応性が極めて高い） | 2.0〜5.0 秒 |
| **Danbooruタグ知識** | イラスト文化タグを十分に保持、基本構文は完璧 | 深いスラング・マイナータグまで完全網羅 |
| **検閲 (Censorship)** | **完全無検閲**（プロンプト指示・アライメント解除版） | **完全無検閲** |

- **運用評価**: 
  - 本ツールの「自然言語からコアタグ3〜5個を抽出する」というタスクにおいては、巨大な **Qwen 3.8** よりも、高速・軽量でVRAMを圧迫しない **Qwen 3.6**（小型クラス）が圧倒的に適している。
  - ComfyUIの画像生成と同一マシンで共存させる場合も、Qwen 3.6 であればVRAMオーバーヘッドを最小限に抑えて並行稼働可能。

---

### 3.2 クラウド API (Gemini API) の検討

高速かつローカルリソースを消費しない手段として、最新の Gemini 世代を対象とする。

| 項目 | Gemini 3.5 Flash-Lite | Gemini 3.8 Flash |
|---|---|---|
| **推論速度** | **0.2〜0.5 秒**（超爆速・最小レイテンシ） | 0.5〜1.0 秒（高品質・高度推論） |
| **ローカルリソース** | **0 MB**（外部API） | **0 MB**（外部API） |
| **APIコスト** | 極小（実質無料枠でほぼ賄える） | 安価 |
| **コンテンツエラー** | **留意が必要**（Safety Filter による拒否リスク） | **留意が必要**（Safety Filter による拒否リスク） |

---

### 3.3 💡 レーティング分離アーキテクチャ（コンテンツエラーの根本回避策）

Gemini API などの商用クラウドモデルを利用する際、最大のボトルネックは「際どい」「エロ」「全裸」といった性的表現に起因する **Safety Filter（コンテンツブロック）** である。
しかし、本プロジェクトのシステム構造を活かすことで、この問題を極めてエレガントに回避できる。

#### 🛡️ 「レーティングは後段で制御する」原則
1. **WebUI には既にレーティング制御がある**:
   - WebUI の自動バッチ生成パネルには、すでに **「🔞 レーティング（`#b-rating`）」** ドロップダウンが存在する（`explicit`, `questionable`, `sensitive`, `general`, 指定なし）。
   - また、`src/server.py` および `danbooru_search_batch_generator.py` には、検索クエリ内の `rating:...` を**後段でパージ・強制上書きする機能**がすでに備わっている。
2. **LLM から性的レーティング判定を切り離す（Decoupling）**:
   - LLM に「このシチュエーションはエロいか？」というセンシティブな判定をさせず、**「純粋な情景・シチュエーションタグ（例: `beach eating_ice_cream 1girl`）」の抽出のみに専念**させる。
   - レーティングタグ（`rating:explicit` 等）の付与は、**WebUI のプルダウン指定やユーザー設定に委ねる**。
3. **絶大なメリット**:
   - Gemini API へのプロンプトから「性的表現の判定」が完全に排除されるため、**Safety Block（コンテンツ拒否）のリスクが構造的に激減**する。
   - ユーザー側も「昼は全年齢（General）で探す」「夜は際どい（Explicit）で探す」という切り替えを、自然言語を変えずに WebUI のプルダウンひとつで自在に制御可能になる。

### 3.4 アーキテクチャ推奨方針（ハイブリッド・プロバイダ設計）

1. **デフォルト（高速・リソースゼロ）**: 
   - **Gemini 3.5 Flash-Lite**（または **3.8 Flash**）
   - レーティング分離アプローチにより、シチュエーション抽出に特化して爆速応答。
2. **完全ローカル・無検閲（プライバシー・ローカル完結）**: 
   - **Ollama / ローカルLLM（Qwen 3.6 小型クラス）**
   - 外部通信なしで動作し、ハードな文脈でも確実にタグ化。
3. **フォールバック機構**:
   - Gemini 側で万が一ブロックやネットワーク不通が生じた場合は、即座にローカル Qwen 3.6 へフォールバック。

## 4. プロンプトエンジニアリング ＆ タグ生成原則

### 4.1 プロンプト設計のコア原則（引き算の美学）

1. **必要最小限の原則**:
   - 出力するタグは **合計 2〜4 個** に厳密に制限する。
   - `[シチュエーション/背景タグ 1〜2個] [アクション/主要モチーフ 1個] [1girl]`
   - （※ `order:` や `rating:` は後段のWebUI/CLIオプションで自在に注入・置換可能とする）
2. **ニッチタグは無理に予測しない**:
   - 「アクセサリー」「ピアス」「体型ディテール」「構図」などは、ユーザーが明示的に求めていない限りクエリに含めない（元投稿側のタグプールに委ねる）。
3. **名詞最優先・動詞合成タグの回避（「eating_ice_cream」トラップの排除）**:
   - Danbooru は英語の自然な「動詞＋名詞」（例: `eating_ice_cream`）のような複合タグを作らず、**「主要名詞（例: `ice_cream` 35,000件超）」** または **「動作名詞（例: `eating` 110,000件超）」** に分解されてタグ付けされる。
   - 実際、Danbooru 上で `eating_ice_cream` の登録投稿件数は **0 件（完全爆死）** であり、`ice_cream` を指定するだけで「アイスを食べている」「アイスを持っている」イラストが数万件ヒットする。
   - したがって、プロンプト指示および事後検証で「動詞＋名詞の過剰な合成タグ」を抑止し、**アイテム・対象を表す単独名詞タグ（`ice_cream`）を優先採用**する。
4. **Danbooru 命名規則の遵守**:
   - 単語間はスペースではなくアンダースコア（`_`）で結合する。
   - デフォルトで `1girl` を付与し、女性単体イラストを優先取得。
5. **Booru検索特性と使い分けの推奨（無料枠2タグ制限の現実）**:
   - **Danbooru**: 無料枠/匿名では「最大2タグまで」のAPI制限が存在する。`word1 word2 sort: rating:` のような3タグ以上のクエリはAPI側で弾かれる。バッチジェネレータ（`danbooru_search_batch_generator.py`）では2タグでAPI取得後に手元で残りをクライアント側判定する機構を持つが、ヒットまでページ繰り待機が多発し実用的ではない。  
     しかし**タグ付け品質はBooru界最高峰**であり、わずか1〜2語（微小装飾や特定モチーフ）から極めて濃厚な装飾タグ群が連鎖するため、「共起継承の輪（xxxxx ring）」の恩恵を最大に享受できる。
   - **Gelbooru**: 3タグ以上の複数タグ・ソート・レーティングの複合検索を無料でも快適に処理できるため、自然言語から複数タグを抽出してダイレクトにバッチ生成へ流し込む場合は Gelbooru の併用・推奨が極めて実用的である。

### 4.2 システムプロンプトの外部管理設計

メンテナンス性・調整容易性を高めるため、LLMへ渡すシステム指示文はPythonコード内に直書きせず、独立したMarkdownファイルとして外部管理する。

- **ファイルパス**: [`src/prompts/natural_search_system_instruction.md`](src/prompts/natural_search_system_instruction.md)
- **読み込み方針**:
  - Pythonスクリプト（`natural_to_danbooru.py`）起動時、上記ファイルをUTF-8で自動ロードする。

  - 将来的なUI（設定タブ等）からのプロンプト微調整・カスタマイズにも自然に対応可能。
